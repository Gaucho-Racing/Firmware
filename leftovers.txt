2. CUSTOM CAN ID TYPE CONVERSION (normalizeCanId / toCanIdOverride)
   File: Web/candoDocument.js
   Problem: canId values in Custom CAN ID are stored as bare uppercase hex
   ("2416" means 0x2416), but routing can_id_override uses "0x"-prefixed hex
   ("0x2416"). No central conversion — callers were inconsistent, causing
   routing overrides to not match their CAN ID messages.
   Fix:
     - Added normalizeCanId(raw): strips "0x" prefix, uppercases, validates hex
     - Added toCanIdOverride(bareHex): wraps normalizeCanId result with "0x"
     - addCustomCanIdDef: stores canId: normalizeCanId(def.canId)
     - updateCustomCanIdDef: when CAN ID changes, sweeps all routing entries
       with the old override and updates them to the new override
     - addRoute / routeEntryExists: normalized comparison so "0x2416" == "2416"
   Status: COMPLETE.

4. COMMENT FORMAT MIGRATION — WEB TOOL (Fixes 1–6)
   Context: The .CANdo format is migrating signal/field comments from YAML
   "#" comment lines to a "comment:" data field with a plain indented block.

   Old format (Custom CAN ID signals):
       - name: "Target Brake Current"
         bit_start: 0
         # Targets the brake current of the motor.
         # This value must be multiplied by 10.

   New format:
       - name: "Target Brake Current"
         bit_start: 0
         comment:
             Targets the brake current of the motor.
             This value must be multiplied by 10.

   Fix 1 — _parseCustomCanIds (candoDocument.js ~line 274)
     Added _inSignalComment flag. Activates on "comment:" at indent 8,
     accumulates continuation lines at indent > 8. Old "#" format still parses
     (backward compat). Status: COMPLETE.

   Fix 2 — _serializeCustomCanIds (candoDocument.js ~line 402)
     Serializer now outputs "comment:\n" + 12-space-indented lines per signal.
     Status: COMPLETE.

   Fix 3 — _parseMsgIds (candoDocument.js ~line 165)
     Added _inFieldComment flag. Key design decision: field keywords ("data
     type:", "units:", etc.) are ALL at indent 6. Continuation lines of a
     comment: block are at indent > 6 (indent 8). The fix restructures the
     indent >= 6 branch into two sub-branches:
       - indent === 6: always resets _inFieldComment, processes as keyword
       - indent > 6 && _inFieldComment: accumulates continuation text
     This resolves a bug where "data type:" after a comment: block was silently
     dropped because the old _inFieldComment guard blocked the keyword.
     Old "#" format still parses (backward compat). Status: COMPLETE.

   Fix 4 — _serializeMessageIds (candoDocument.js ~line 372)
     Serializer now outputs "comment:\n" + 8-space-indented lines per field.
     Status: COMPLETE.

   Fix 5 — formMessageDef.js parseMessageFromRaw (~line 75)

     text directly (bypasses candoDocument.js). Same _inComment flag pattern

     Status: COMPLETE.

OUTSTANDING FAILURES (2/142 tests)
--------------------------------------------------------------------------------

Both failures are in "Source of truth — Perl parser parity" section of the
test suite. They run the Autogen/CAN/Src/ Perl parsers against the serialized
output and compare generated C headers to the original.

FAILURE 1: CANparser (Custom CAN ID section)
  Test: "CANparser (Custom CAN ID section): serialized output produces identical header"
  Error: "YAML::XS::Load Error: mapping values are not allowed in this context
          was found at document: 1, line: 319, column: 17"

  Root cause: CANparser.pl calls YAML::XS LoadFile() on the entire .CANdo
  file. Our new "comment:" block format is NOT valid YAML. Specifically,
  continuation lines containing ":" (like "1: OK, 0: Timeout") are
  interpreted by YAML::XS as nested mapping keys, causing a parse error.

  Example of what we serialize (NOT valid YAML):
      comment:
          1: OK, 0: Timeout        ← YAML::XS sees this as a nested map

  Valid YAML literal block would be:
      comment: |
          1: OK, 0: Timeout        ← YAML literal block scalar (valid)

  What needs to change: Either:
    (a) Update CANparser.pl to parse the file line-by-line instead of using
        YAML::XS, OR
    (b) Update our serializer to use "comment: |" literal block scalar syntax,
        AND update our parser to handle the "|" indicator after "comment:",
        AND verify the real .CANdo file uses this format on caroline_com branch.

  Note: CANparser.pl does NOT use the comment field at all — it only reads
  "CAN ID" to generate enum values. So the YAML parse failure crashes the
  whole file load, not just comment handling.

FAILURE 2: STRUCTparser (Message ID structs)
  Test: "STRUCTparser (Message ID structs): serialized output produces identical header"
  Error: Headers differ.

  Root cause: STRUCTparser.pl has a parse_descriptions() function that
  collects "# comment" lines from the Message ID section and embeds them as
  C docstrings. The regex it uses is:
      /^\s+ \# \s* (.*)/smx
  This ONLY matches "#" lines — it does NOT handle "comment:" fields.
  After our migration, comments come through as "comment:" blocks in the
  serialized output, so parse_descriptions() finds nothing, and the generated
  C header has empty/missing docstrings compared to the original.

  What needs to change: Update STRUCTparser.pl's extract_desc_from_array()
  (called by parse_descriptions()) to also recognize the "comment:" block
  format, accumulating indented continuation lines.

  File to change: Autogen/CAN/Src/STRUCTparser.pl
  Function: extract_desc_from_array() (~line 78) and/or parse_descriptions()
  (~line 40).
